# Contributing to benchlens

Thanks for helping. This file covers the development setup, how the code is laid out, the rules every
change follows, how to add a vmbench version, how to run the tests, and how a change gets merged.
To report a security problem, see [SECURITY.md](SECURITY.md) instead of opening an issue.

## Development setup

| Tool | Version | For |
|---|---|---|
| Rust | 1.89 or later (`rustup`), with `rustfmt` and `clippy` | everything (`rust-version` in `Cargo.toml`) |
| a C compiler | any | the bundled SQLite of `rusqlite` |
| `wasm32-unknown-unknown` target | `rustup target add wasm32-unknown-unknown` | the WebAssembly build of the verdict rule |
| `wasm-bindgen-cli` | **exactly 0.2.130**, the version pinned in `crates/wasm/Cargo.toml` | `scripts/build-wasm.sh` |
| Node.js | 24 | the WASM golden test, the end-to-end and export tests (Playwright) |
| Python 3 | any recent | `tools/golden.py`, only when refreshing the golden file |
| `wasm-opt` (binaryen) | optional | makes the WASM build smaller when on `PATH` |

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.130 --locked
cargo build                                   # debug build; target/debug/benchlens
```

A debug build reads `web/` from disk, so editing the web UI needs no rebuild: start the server and reload.

```bash
cargo run -p benchlens -- --db /tmp/poc.db import --registry examples/poc-2026-11/registry.tsv tests/fixtures/v0.2.1 tests/fixtures/v0.2.3
cargo run -p benchlens -- --db /tmp/poc.db serve          # http://127.0.0.1:8080
```

## Workspace layout

```
crates/rules    benchlens-rules: the verdict rule, statistics, metric tables (catalog/*.txt). No I/O, no
                SQLite, so it also builds for wasm32. The rule here is vmbench's; see the ground rules.
crates/core     benchlens-core: the data contract (reading result folders and archives), import, registry,
                SQLite store and its views, compare, inbox. Re-exports benchlens-rules.
crates/server   benchlens-server: axum server, JSON API v1, auth, upload, config (benchlens.toml), the static
                HTML export; embeds web/ in release builds.
crates/cli      the `benchlens` binary: every subcommand (main.rs) and export csv/json (export.rs).
crates/wasm     benchlens-wasm: benchlens-rules compiled to WebAssembly for the browser and the HTML export.
web/            the web UI: plain HTML, CSS and JS modules, d3 vendored, no build step (web/README.md).
web/wasm/       generated by scripts/build-wasm.sh and committed.
docs/           api.md (API contract), contract.md (what is read from vmbench), guide.md, walkthrough.md,
                plan.md and reviews/ (project plan and lead reviews), api-examples/ (generated).
tests/fixtures/ real vmbench result folders, one folder per vmbench version.
tests/golden/   compare.json: vmbench's own verdicts for fixture pairs (written by tools/golden.py).
tests/e2e/      Playwright suite against `benchlens serve` (tests/e2e/README.md).
tests/export/   the HTML export opened from disk, offline, checked against `benchlens compare --json`.
tests/wasm/     the golden pairs run through the WASM build in node.
tools/golden.py writes tests/golden/compare.json from vmbench's report.py.
scripts/        build-wasm.sh, test-wasm.sh, e2e.sh.
examples/       poc-2026-11/registry.tsv: tags for the POC runs.
```

## Ground rules

1. **The verdict rule is vmbench's.** benchlens must say exactly what `vmbench report compare` says. Do not
   change `crates/rules` (verdict, statistics) or how `crates/core/src/compare.rs` pools values unless vmbench
   changed first. The golden tests (`crates/core/tests/golden.rs`, and `scripts/test-wasm.sh` for the WASM
   build) compare every metric of the fixture pairs with vmbench's own verdicts and must pass on every branch.
2. **Real data only.** Tests, examples, docs and screenshots use `tests/fixtures/` and what the code prints
   for them (`benchlens compare ... --json`, `benchlens runs --json`, the API). No invented numbers; docs show
   commands that were run, with their real output.
3. **The API contract is [docs/api.md](docs/api.md).** A change to a JSON shape changes api.md,
   `docs/api-examples/` (regenerated), the server and the web UI in the same change.
4. **No new runtime services.** One binary, one SQLite file. A dependency that needs a system library or a
   network service needs a note in the PR.
5. **Untrusted input everywhere**: archives, uploads, tags, query strings, HTML. Never build SQL from strings,
   never write outside the configured data folder, never follow links; values go into pages with
   `textContent`, never `innerHTML`.
6. Before every push: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all`.

## Adding a vmbench version

When vmbench releases a version whose metric table differs from the built-in ones (users can add a table at
run time with `benchlens catalog add`, but a release should know it):

1. **Metric table.** With the new vmbench: `vmbench run --metrics > crates/rules/catalog/vmbench-X.Y.Z.txt`,
   and add `("X.Y.Z", include_str!("../catalog/vmbench-X.Y.Z.txt"))` to the built-in list in
   `crates/rules/src/catalog.rs`.
2. **Fixture.** Add at least one real result folder of that version as
   `tests/fixtures/vX.Y.Z/<folder>/` with the four files benchlens reads (`meta.json`, `results.tsv`,
   `status.tsv`, `hardware.json`; leave out `report.md` and logs). Add `"vX.Y.Z"` to `FIXTURE_VERSIONS` in
   `crates/core/src/testing.rs`. If `meta.json` has a new `schema`, benchlens must learn it first
   ([docs/contract.md](docs/contract.md#when-vmbench-changes-its-format)).
3. **Golden file.** List new pairs in `PAIRS` of `tools/golden.py` (the new version against itself and
   against an older version), then, from the repository root, with a checkout of that vmbench:
   `python3 -I tools/golden.py ../vmbench`. Commit `tests/golden/compare.json`.
4. **API examples.** `cargo run -p benchlens-core --example api_examples` rewrites `docs/api-examples/*.json`
   from the fixtures; check the diff and update `docs/api.md` if anything it states changed.
5. Run every suite below. Tests that count fixture runs or name fixture folders may need updating; the e2e
   suite reads its counts from the fixture folders.

## Running the tests

| Suite | Command | What it checks |
|---|---|---|
| format, lint | `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` | style, warnings |
| Rust tests | `cargo test --all` | unit and integration tests of every crate, including the golden verdicts, import and archive safety, store, inbox, every API endpoint, upload and auth, export |
| rules for wasm32 | `cargo build -p benchlens-rules --target wasm32-unknown-unknown` | the rule stays free of I/O |
| WASM golden | `scripts/test-wasm.sh --build` | rebuilds `web/wasm/` and runs every golden pair through it in node |
| end-to-end | `scripts/e2e.sh` | release build, three servers on the fixtures (open, token, private), the Playwright suite in `tests/e2e/`, then `tests/export/run.sh` |
| export only | `NODE_PATH=tests/e2e/node_modules tests/export/run.sh` | the offline HTML export against `benchlens compare --json` |

`scripts/e2e.sh` installs the Playwright package itself (`npm ci` in `tests/e2e`) when needed; the browser
comes from `npx playwright install chromium` (see [tests/e2e/README.md](tests/e2e/README.md), also for
machines without root). If you change `crates/rules` or `crates/wasm`, rebuild with `scripts/build-wasm.sh`
and commit `web/wasm/` (the bytes depend on the rustc version; CI only warns when they differ). CI
(`.github/workflows/ci.yml`) runs all of the above plus a Docker build on every pull request.

## How a change gets merged

The project is built in tasks listed in [docs/plan.md](docs/plan.md), often by several people or agents at
once:

1. **One task, one branch.** Branch from `main` as `<milestone>/<task-id>-<slug>` (for example
   `m3/h-docs`), ideally in its own worktree, and stay inside the files the task owns. Need a change
   elsewhere? Keep it as small as possible and say so.
2. **Commit on the branch, then stop.** Task branches are not pushed as PRs by their authors.
3. **Lead review.** The lead reviewer reads the whole diff against the task, the API contract and the
   ground rules, fixes small issues in separate `review(...)` commits, refactors across branches, integrates
   them in an `integration/*` branch with every suite green, writes the review in `docs/reviews/`, and opens
   the pull request.
4. **The owner merges.** A pull request without a lead review summary is not merged.

Outside contributors are welcome to open a pull request directly: it goes through the same lead review
before the owner merges it. For anything larger than a fix, open an issue first so it can become a task.
