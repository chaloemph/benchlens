## F26: lowest-priority image default (`BENCHLENS_DEFAULT_ALLOWED_HOSTS`)

The image sets `ENV BENCHLENS_DEFAULT_ALLOWED_HOSTS=localhost` instead of `BENCHLENS_ALLOWED_HOSTS`.
`Settings::resolve` picks `allowed_hosts` from flag > `BENCHLENS_ALLOWED_HOSTS` > file > default > none. The
default is `#[serde(skip)]` on a `deny_unknown_fields` layer, so `default_allowed_hosts` in benchlens.toml is
an error (tested). Checked:

- **The check is never turned off by the new code path.** It is off only when the effective list is empty on a
  non-loopback listener with a token (`checks_host`, unchanged). The new path can only yield an empty list
  when every source is empty, or `BENCHLENS_ALLOWED_HOSTS` is set without names (the documented opt-out). An
  empty or blank file list (`[]`, `[" "]`) falls through to the default, so a mounted file can no longer turn
  the guard off in the image (in 0.1.2 the env beat it anyway).
- **A file whose list omits `localhost`**: the list is non-empty, so the check stays on; `localhost` and IP
  addresses are served by the fixed rule in `check_host`. Docker-checked (`bench.lan` file: localhost 200,
  127.0.0.1 200, evil 403).
- **Names**: every source goes through `check_hosts` (trim, trailing dot, lower case, empty entries dropped;
  scheme, port, brackets, inner blanks refused at start-up). An invalid default is an error naming
  `BENCHLENS_DEFAULT_ALLOWED_HOSTS`; an invalid file list is an error unless a flag or the variable replaces it
  (as in 0.1.2). Duplicates are harmless (`contains`). Request-side names are normalised the same way.
- **Nothing in a request influences the source**: it is fixed at start-up in `Settings`, copied into
  `Access` by `Access::for_settings`.
- **Found, fixed** (review commit): `BENCHLENS_ALLOWED_HOSTS=" "` (or `,`) was "set" (non-empty string) but
  held no names, so it turned the check off *and* hid a mounted file's list (with a warning), while `=` (empty)
  used the file. Same as 0.1.2, but inconsistent with the documented opt-out and less safe. Now a value with
  no names counts as empty: not set, drops the default, the file's list is used when present. CHANGELOG,
  guide and api.md say so; precedence test cases added.

## F25: the 403 names the setting of the source

`HostsSource` (Unset, Flag, Env, File, DefaultEnv) is recorded in `Settings`, passed by
`Access::for_settings`, used by `host_refused` and `hosts_served` (start-up line `(from <source>)`). The 403
never prints configured names or the token: the detail is built from fixed text plus the refused name itself
(only when it is a plain name, else no name), checked per source in
`auth::tests::host_refused_names_the_setting_of_the_source` and in the Docker matrix. The 403 does reveal
which kind of source is in use (variable vs file vs default); that is the purpose of F25 and not sensitive.

Found, fixed (review commit):

- **Flag source named the wrong setting**: `HostsSource::Flag` shared the Env text ("add it to
  BENCHLENS_ALLOWED_HOSTS"), but a flag beats the variable, so that would not work. No `serve` flag exists
  today (only programmatic callers), but the text now names the command-line list. Test split.
- **"or set a token" when a token would not help**: without a token on a non-loopback listener the detail
  ended in ", or set a token" for every source. With a non-empty list (the image default, a file, the
  variable) a token keeps the check on and the name is still refused; the hint is right only when no list is
  set. Pre-existing in 0.1.2 (the image always had a list), but it is exactly what F25 is about. Now added only
  when the list is empty; unit test added. Docker: no-token container now says only the settings.

The start-up warning about a hidden file list fires only for Flag/Env with a different non-empty file list
(tested for each case of `hosts_precedence_for_every_source`); its text no longer mentions the image.
