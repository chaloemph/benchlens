# Review: M7 follow-up F27 (branch `m7/f27`)

Reviewer: L. Branch: one task commit (b46153a) on main 8f5a069 (0.1.3), plus two `review(f27)` commits.
Verdict: **accepted with small fixes** (below). No version bump, CHANGELOG stays `[Unreleased]`.

## What the branch does

`Settings::warnings()` adds one start-up line when the Host check is off and reads are open:

```text
warning: listening on <addr> with no Host check: any Host name is served, so a DNS rebinding web page can read the public data (writes still need the token); set allowed_hosts in benchlens.toml or BENCHLENS_ALLOWED_HOSTS=name to turn the check on, or read_public = false to keep reads behind the token
```

Behaviour is unchanged; only stderr gains the line.

## Findings

- **Condition matches the guard: yes, now by construction.** The task repeated the condition
  (`token && !is_loopback && allowed_hosts.is_empty()`), which matched `Access::checks_host` but could drift.
  Fixed: the warning asks `Access::for_settings(self).checks_host()` (now `pub(crate)`), plus
  `read_public`. Checked against the combinations, in unit tests and live: no list (warns); a list from the
  variable, the file, the image default or a flag layer (quiet); `BENCHLENS_ALLOWED_HOSTS=` / `" "` / `","`
  with the image default and no file (warns); an empty file list `allowed_hosts = []` (counts as not set:
  warns, and the server serves any Host, confirmed); a list but no token (only the no-token warning, Host
  check on: evil 403); loopback with a token, also `[::ffff:127.0.0.1]` (quiet, check on). There is no
  `--allowed-hosts` CLI flag; the flag source is reachable only from code (F29).
- **`read_public = false` stays quiet: accepted.** With a token, `read_public = false` and no list, a
  rebinding page (Host `evil.example`, checked live and in Docker) gets 200 for `/api/health`
  (`{"benchlens":"0.1.3","db_layout":2,"runs":N}`), `/` and the UI files, 401 for every data route
  (`/api/runs`, `/api/groups`, ...), 404 for unknown `/api` paths. It never sees the token (a bearer header
  the UI keeps per origin, not a cookie). So the exposure is the version and the run count, which anyone who
  reaches the port directly gets too; warning on that would push users who chose a private server towards a
  setting they do not need. The task's comment and plan row said "nothing readable": corrected in the code
  comment, SECURITY.md, the guide and the plan.
- **Text**: one line like the other warnings; prints the listen address (as the no-token warning does), never
  the token or the configured names (asserted in unit, router and binary tests; Docker logs grepped for the
  token: 0 hits). Wording is plain enough: it says what is open, what still needs the token, and the two ways
  out. Like the no-token warning it prints the configured address, so `--listen 0.0.0.0:0` shows `:0` (the
  first start-up line has the real port); not worth a change.
- **Tests fail without the change**: with the warning disabled, `warns_when_the_host_check_is_off`, the
  hardening router test and two of three `serve_warnings` tests fail (the third checks quiet cases).
- **Binary test robustness** (fixed): the test sent SIGTERM right after reading `Host names served:`, but the
  SIGTERM handler is installed only once `axum::serve` polls the shutdown future, so an early signal could
  kill the process before the warning or `benchlens stopping` was written (flaky). It now waits until the
  server answers `GET /api/health` on the bound port, and a drop guard kills the child if a test panics before
  stopping it. stderr is drained by a thread, so a slow or chatty stderr cannot block; every wait has a
  timeout (20 s start-up, 20 s serving, 10 s stop). 15 repeated runs green, no process left behind.
- **Docs**: the guide's captured outputs were re-run (`serve --listen 0.0.0.0:18085` with a token, and the
  Docker opt-out `docker logs`): identical text. Relative links and anchors in the changed files resolve.
